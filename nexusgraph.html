nexusgraph

NexusGraph

a structured framework for Collaborative AI Workflows based on LangGraph

  • news
    • [25/12] support FrameWork version 0.0.1 publish

Features

NexusGraph is an enhanced framework built on top of LangGraph that standardizes node, state and workflow definitions while enabling YAML-based configuration. By introducing structured abstractions and declarative setup, NexusGraph makes complex agent system more accessible, maintainable, and team-friendly.

Advantages

  • 🎯 Standardized Components

    NexusGraph offers clear and detailed patterns with comprehensive documentation for defining nodes, states and workflows, thereby reducing decision fatigue and ensuring consistency in large codebases. Compared with LangGraph, we offer Node templates instead of functions, which enables the implementation of nodes to be reused on a large scale.

  • ⚙️ Json/YAML-Powered Configuration

    Design and modify your agent workflows through simple YAML files—separating logic from configuration and enabling rapid prototyping without code changes.

  • 🔧 Decoupled Node & Agent Lifecycle

    Node development is fully decoupled from agent assembly—build and test nodes in isolation, then wire them together via YAML at configuration time. This enables true parallel development across large teams, eliminating bottlenecks and merge conflicts.

  • 🤝 Built for Teams

    With clear conventions and declarative syntax, NexusGraph lowers the barrier to entry for new developers and streamlines code reviews, making it ideal for collaborative development.

Why use NexusGraph?

While LangGraph offers flexibility, NexusGraph trades some of that freedom for productivity and predictability—helping teams ship reliable AI agents faster without sacrificing power.

Usage

install

git clone git@github.com:NexusGraph/nexusgraph.git
cd nexusgraph
pip install -e .

# for developer
pip install -e .[dev]

python tools/nexus_graph_cli.py --list <key>              # Show details for specific component
python tools/nexus_graph_cli.py                           # Same as --list (default behavior)

example

We decoupled the development of Node from the specific Workflow, enabling the development team to maximize reusability and collaboration in completing the development of the Node collection. When we need to build a workflow, we only need to configure YAML to determine the relationship between data and connections between nodes, and then they can be reused in a large number of unrelated workflows.

from nexusgraph.bases.workflow import WorkFlowBase
from langgraph.types import Command
from langgraph.checkpoint.memory import MemorySaver
from nexusgraph.utils.dummy_chat_openai import DummyChatOpenAI
from nexusgraph.states.emails.email_agent import EmailClassification

workflow = WorkFlowBase.from_config(
    "example/email_reply.yaml",
    llm=DummyChatOpenAI(model="gpt-4"),
    llm_struct=EmailClassification,
)

app = workflow.compile(checkpointer=MemorySaver())
app.visualize_graph()

result = app.invoke()

while True:
    if "__interrupt__" in result:
        for i in range(len(result["__interrupt__"])):
            print(f"interrupt info[{i+1}]:", result["__interrupt__"][i])
        print()

        approved = input("approved draft_response or not [y/N]:")

        interrupt_info = result["__interrupt__"][0].value
        if "y" in approved.lower():
            human_decision_data = {
                "inputs": {
                    "human_approved": True,
                    "edited_response": (
                        interrupt_info.get("tips", {}).get("draft_response", "") or ""
                    )
                    + "and response has been reviewed and approved.",
                }
            }
        else:
            human_decision_data = {
                "inputs": {
                    "human_approved": False,
                    "edited_response": "agent give '"
                    + interrupt_info.get("tips", {}).get("draft_response", "")
                    + "' and be refused by human.",
                }
            }
        result = app.invoke(Command(resume=human_decision_data))
        continue
    else:
        break
print("exit.")

YAML/JSON define graph

You can also read "nexusgraph.dataclass.workflow" to directly understand the YAML rules.

1. full template

# head of config
version: v1.0               # [optional] yaml version for future, no used at this time
debug: false                # [optional] True will print debug info, such as graph node detail
key_lost: remain            # [optional] "exception", "warning", "remain"(default), 
                            # if key lost in alias dict, remain and warning will use key=f"{key}

# states config
states:                     # list like state, use only one at this time         
- name: <state_id>          # any sole string as you like
  type: <StateBase>         # StateBase type that can be view be cli-tools
  inits:                    # [optional] you can give init value for your states  {} is ok
    file:                   # [optional] you can give value from YAML/JSON file
    values:                 # [optional] you can give value from YAML/JSON file, will merge with file and have a higher priority

# nodes config
nodes:
- name: <node_id>
  type: <NodeBase>
  retry_policy:             # [optional] add retry_policy to curent node
    max_attempts: 3         # [optional] args for retry_policy
  # define key alias
  key_alias:                # refer runtime binding from node [INPUT,OUPUT] params to key in state. 
                            # param_names can be queried by cli-tools or website doc
    file:                   # [optional] you can give value from YAML/JSON file
    values:
      <param_name>: <alias> # [optional] you can give value from YAML/JSON file, will merge with file and have a higher priority
                            # if `param_name: null` is give, Node will get `value=default`, default is Node param default value

                            # support param_name: "key1.key2.key3":
                            # [INPUT] Node will get `$param_name=state["key1"]["key2"]["key3"], value=None means not exist
                            #         if `param_name: null` is give, Node will get `value=default`, default is Node param default value
                            # [OUTPUT] Node will update value to `$param_name="key1.key2.key3"`
                            # [TMP_OUTPUT] Node will update value to `$param_name="key1.key2.key3"`, usually 
                            #               this key can be random, it make no binding with state and runtime, used for Send in Parallel
                            # [RUNTIME] Node will get `$param_name=runtime_dict["state_key"]`, `runtime_dict` is init by kwargs give for  
                            #           init node, or give by runtimes: {} below

  # give runtime value by config
  runtimes:
    file:                   # [optional] you can give value from YAML/JSON file, will merge with values
    values:
      <key>: <value>        # null means use param default. or give as real param for node (get `$key=value`)

  # set edges
  edges:                    # you can use <START> and <END> as special node name
                            # param_names can be queried by cli-tools or website doc
    start: false            # [optional] true will add <START> as previous node
    nexts:                  # [optional] null means no addition next. support list[str] or str. node will always run after all 
      - <node_name1>        # previous nodes done. Even without data transmission, edges can still be constructed. 
      - <node_name2>        # if no outbounds, you need add at least one as next node     

    outbounds:              # if nodes require [NODE_KEY], you must set here, then node select condition next
      file:                 # [optional] you can give value from YAML/JSON file, will merge with values
      values:               # [optional] only give if node require
        <bug_next>: <node_name3>  
        <fail_next>: <node_name4>
        <success_next>: <node_name5>

Support Nodes

Derive from NodeBase Derive Support

  • [1/14] BugTrackingNode: Node for managing bug tracking tickets.
    • detail describe: This node interfaces with the bug tracking system to create new tickets or update existing ones based on email content classified as bug reports.
  • [2/14] DraftResponseNode: Node for drafting email responses.
    • detail describe: This node generates email responses using context from search results, customer history, and the original email content. It determines whether human review is needed based on urgency and intent.
  • [3/14] EmailClassifyNode: Node for classifying emails based on content and intent.
    • detail describe: This node uses a language model to analyze email content and classify it according to intent, urgency, topic, and provides a summary. Based on the classification, it routes the email to the appropriate next node in the workflow.
  • [4/14] HumanInputNode: Get human input numbers
  • [5/14] HumanReviewNode: Human review node for email agent workflow.
    • detail describe: This node interrupts the workflow to present a generated email response to a human reviewer for approval or editing. Based on the reviewer's decision, it either proceeds to send the response or ends the workflow.
  • [6/14] ParallelTranslateNode: Parallel call SignalTranslateNode
  • [7/14] ReadEmailNode: Email Reading Node
    • detail describe: This node is responsible for reading email content from the workflow state and converting it into a format suitable for further processing. It serves as the starting point in the email processing workflow, typically used to extract and prepare email data. In a production environment, this node would connect to an actual email service (such as SMTP, IMAP, or email APIs) to fetch email content.
  • [8/14] SearchDocumentationNode: Node for searching documentation based on email classification.
    • detail describe: This node searches the knowledge base for relevant information based on the intent and topic extracted from email classification. It stores the search results for use in response drafting.
  • [9/14] SendReplyNode: Node for sending email replies.
    • detail describe: This node is responsible for sending the final email response to the customer. In a production environment, it would integrate with an email service provider or SMTP server to deliver the message.
  • [10/14] SignalTranslateNode: Translate numbers to english, only support 0~9
  • [11/14] SystemEndNode: Node that auto add as next node
  • [12/14] SystemStartNode: Node that auto add as previous node
  • [13/14] SystemUpdateValueNode: Node that update {key:value} into state
  • [14/14] ViewNode: Print result of translate demo
